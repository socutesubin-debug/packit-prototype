> 적용 대상: Figma 화면·프로토타입, Claude Code/Codex 구현, 이미지 제작 및 디자인 QA

## 1. 목적과 제품 범위

개정 인터뷰에서 아래 다섯 가지를 첫 버전의 기준으로 확정했다.

| 결정 | 확정 내용 |
|---|---|
| 목적 | 일본 쇼핑 여행의 준비부터 현지 구매, 구매 기록까지 한 앱에서 끝낸다. 흩어진 구매 후보를 모으고, 현지에서 찾아 사고, 산 물건을 캐리어 컬렉션으로 남긴다. |
| 타깃 | **일본 쇼핑 여행을 가는 2030.** 여행 전 캡처·링크로 살 것을 모으고, 현지에서 매장과 상품을 빨리 찾고 싶어 하며, 다른 여행자의 발견을 참고하는 사람. |
| 핵심 경험 하나 | **Carry를 열면 내가 산 물건들이 하나의 컬렉션으로 모여 있는 모습을 한눈에 본다.** (1판과 동일) |
| 포함 범위 | 피그마 「시안2」 전체: 여행 생성, 저장(스크린샷 추출 포함), 목록과 우선순위 스와이프, 제품 상세·현지어 카드, 지도·매장 상세, 매거진(발견 피드·작성글·프로필·글쓰기), 캐리어 꾸미기(겉면 스티커·내부·구매 리스트·후기). |
| 완료 기준 | 타깃 사용자 5명 중 최소 4명이 각자 도움 없이 후보 저장 → 앱을 다시 열어 목록에서 찾기 → 구매 완료 → Carry에서 기록 확인 → **캐리어 꾸미기**까지 마친다. |

핵심 흐름:

**발견 → 저장 → 우선순위 정하기 → 목록에서 다시 찾기 → 현지에서 매장·현지어 카드로 구매 → 구매 완료 → Carry 컬렉션 확인 → 스티커로 꾸미기**

- 여행 전: 스크린샷·링크·사진으로 구매 후보를 저장하고 스와이프로 우선순위(꼭 살래·고민·안 살래)를 정한다. 매거진에서 다른 여행자의 발견을 내 여행에 저장한다.
- 여행 중: 목록과 지도에서 후보와 매장을 찾고, 현지어 카드로 점원에게 묻고, 구매 완료를 체크한다.
- 여행 후: Carry를 열어 실제 구매한 물건의 컬렉션을 보고, 후기를 남기고, 겉면을 스티커로 꾸민다. 내 발견을 매거진에 올린다.

저장한 후보는 목록에 남고, 구매 완료한 물건만 Carry에 들어간다. 핵심 경험은 여전히 Carry이며, 다른 기능은 Carry가 채워지도록 돕는 역할이다.

## 4. Creative Concept — The Art of Collecting

**정돈된 인터페이스 위에 실제 물건이 모이고, 내가 꾸민 캐리어로 여행이 드러나는 디지털 캐리어.**

- **Soft Minimal**: 큰 정보 위계, 충분한 여백, 둥근 형태, 적은 UI 장식.
- **Realistic Objects**: 실제 구매품의 형태·질감·패키지가 취향을 전달한다.
- **Personal Archive**: 사용자의 구매와 기록이 주인공이다. 샘플 상품으로 빈 기록을 채우지 않는다.
- **Playful Craft**: 스티커를 붙이고 물건을 직접 놓는 손맛이 재미를 만든다. 재미는 장식 효과가 아니라 사용자가 직접 하는 행동에서 나온다.

**세련됨 50 / 재미 50**은 픽셀 면적이나 색 사용 비율이 아닌 브랜드 인상이다.

- 세련됨은 정렬·타입·여백·절제된 색에서 만든다.
- 재미는 실제 수집품, 스와이프로 고르는 손맛, 스티커 꾸미기, 구매품이 캐리어에 담기는 반응에서 만든다.
- 모든 화면을 50:50으로 기계적으로 나누지 않는다. 목록·저장은 세련됨 쪽, Carry·스와이프는 재미 쪽으로 기운다.

## 5. Color Direction — Lavender + Neutral

**아래 HEX는 개정 확정 팔레트다.** 피그마 「시안2」의 색을 기반으로 하되, 대비 기준(일반 글자 4.5:1, 아이콘·필수 경계 3:1)에 못 미치는 값은 접근성 보정값으로 바꿨다. 괄호 안 대비는 `#FAFAFA` 배경 기준이다(표면 `#FFFFFF`에서는 조금 더 높다).

### 5.4 그림자

| 레벨 | 값 | 적용 |
|---|---|---|
| None | 없음 | 콘텐츠 카드(목록 행, 상품 카드, 정보 카드)의 기본값 |
| Soft | `0 2px 8px rgba(0,0,0,0.06)` | 떠 있는 작은 컨트롤: 원형 뒤로가기·검색·지도 버튼 |
| Float | `0 4px 16px rgba(0,0,0,0.06)` | 하단 네비, 지도 위 매장 카드, 스와이프 카드 |
| Sheet | `0 -4px 24px rgba(0,0,0,0.06)` | 아래에서 올라오는 시트 |
| Brand Glow | `0 4px 12px rgba(134,130,242,0.4)` | + 버튼(FAB)에만 |

제작 규칙:

- 그림자는 **떠 있는 요소**(화면 위를 덮는 네비·FAB·시트·지도 위 카드·스와이프 카드)에만 쓴다. 스크롤되는 콘텐츠 카드는 그림자 없이 면과 여백으로 구분한다.
- 불투명도 0.08을 넘기지 않는다(Brand Glow 제외). 3D bevel, 유리 효과, hover lift는 쓰지 않는다.
- 상품 컷아웃에는 인공 그림자를 넣지 않는다(§8).

### 5.5 색 제작 규칙

- 중성색이 바탕이고 보라는 행동과 선택의 초점이다. 한 화면에서 보라 요소가 서로 경쟁하지 않게 한다(+ 버튼 하나가 기본).
- 주요 행동 버튼은 Ink Button(`#24222D`)이다. 보라는 버튼 면보다 FAB·선택 표시·짧은 강조에 쓴다.
- 카테고리별 무지개색, 형광 Yellow(`#DFFF3F`), 넓은 warm beige 배경, 파스텔 다색 칩 체계를 쓰지 않는다.
- 구매품·현장 사진의 원래 색은 유지한다. 사진 속 다색과 UI의 상태색은 구분한다.
- 구매 완료는 체크 표시와 '샀어요'·'구매 완료' 글자로 표현한다. 색만으로 구매·선택·오류를 구별하지 않는다.
- 브랜드 HEX를 가독성 때문에 임의로 바꾸지 않는다. 대비가 부족하면 위 표의 보정값을 쓰거나 새 보정값을 제안해 이 문서에 추가한다.
- 외부 브랜드 버튼(카카오·애플)은 각 사의 공식 규격을 따른다.

## 6. Typography & Layout — Clean Sans-serif, 짝수 규칙

### 6.1 글꼴

- 한국어·영문·숫자 UI와 본문: **Noto Sans KR** (가변 폰트, 400–700).
- 현지어 카드 등 일본어 문장은 Noto Sans KR의 일본어 글리프 또는 시스템 일본어 폰트로 표시하고, `lang="ja"`를 지정한다.
- 자간은 -3%(`-0.03em`)를 기본으로 한다.
- 제목·여행명에도 Sans-serif를 사용한다. Editorial Serif를 포인트로 다시 도입하지 않는다. (예외: 글쓰기 툴바의 'Aa' 서식 아이콘은 아이콘 표현으로 허용)
- 위계는 크기·굵기·여백으로 만든다. 과도한 대문자, 넓은 자간, 장식적 활자로 분위기를 보충하지 않는다.
- 긴 상품명은 2줄에서 자르고, 상세 화면에서는 전체를 보여 준다.

### 6.2 짝수 규칙 (확정)

- **모든 레이아웃 값은 짝수**다: 크기, 간격, 여백, 라운드, 아이콘 크기, 글자 크기, 줄 높이.
- 피그마에 홀수가 있으면 **가장 가까운 짝수**로 바꾼다. 예: 이미지 92×75 → 92×76, 간격 3·9·17 → 4·8·16, 아이콘 19·21 → 20, 글자 13px → 14px.
- 줄 높이는 배수(1.4 등)로 두지 않고 **짝수 px로 고정**한다.
- 테두리 두께는 1px(또는 2px)를 쓴다. 0.75px 같은 소수 두께는 쓰지 않는다.
- 최소 터치 영역은 44×44px이다.

## 7. Imagery

### 7.1 상품 = Realistic Cutout

1. 실제 구매품 또는 저장 대상의 사진을 쓴다. 실물의 형태가 식별되어야 한다.
2. 상품은 배경을 제거한 투명 이미지로 만든다. 외곽의 흰 테두리, 배경 잔여물, 잘린 뚜껑·포장 모서리를 검수한다.
3. 원본 종횡비와 패키지 색·로고·제품명을 보존한다. 늘이기, 가짜 라벨 생성, 다른 상품으로 교체하지 않는다.
4. 인공 drop shadow, 3D bevel, 광택 효과를 넣지 않는다. 강한 바닥 그림자는 지우고 제품의 자연스러운 명암은 유지한다.
5. 투명 여백을 제외한 실제 바운딩 박스로 크기와 정렬을 판단한다.
6. 표시 크기의 2배 해상도로 준비한다.
7. 컷아웃이 없거나 실패하면 원본 사진을 정돈된 썸네일로 보여 준다. 사진이 없으면 중성 placeholder와 이름을 쓴다.

예외: 캐리어 내부에서 후기 평가를 표시할 때는 컷아웃 외곽에 2px 상태색 윤곽선을 둘 수 있다(최고에요 초록, 별로에요 주황). 이것은 그림자가 아니라 상태 표시다.

### 7.2 현장 = 실사 사진

1. 매거진 커버·발견 글, 매장 상세, 글쓰기에 첨부한 사진은 배경이 있는 실사 사진 그대로 쓴다.
2. 비율에 맞춰 잘라(cover) 쓰되, 주요 피사체가 잘리지 않게 한다.
3. 캐릭터·브랜드가 크게 찍힌 사진은 사용자 게시물로만 쓴다. 공개 홍보물(포트폴리오·스토어 이미지)에 쓸 때는 권리를 확인한다.
4. 사진 위 글자(매거진 커버 제목)는 아래쪽 어두운 그라데이션 위에 흰 글자로 올리고, 대비를 확인한다.

### 7.3 스티커·캐리어

- 스티커는 Packit이 제공하는 세트(도쿄·도쿄타워·오사카·후지산·오니기리·벚꽃·PACKIT·보딩패스·마네키네코 등)를 쓴다. 흰 테두리 die-cut 스타일로 통일한다.
- 스티커는 캐리어 겉면에만 붙는다. 구매품보다 크게 화면을 주도하지 않게 기본 크기를 제한한다.
- 캐리어는 실사 캐리어 이미지에 색을 곱해(멀티플라이) 색상별로 만든다. 색은 화이트·블랙·옐로·블루·핑크 다섯 가지다.

## 8. Composition

### Carry: 사용자가 직접 만드는 컬렉션

- **겉면**: 사용자가 스티커를 끌어서 붙이고, 옮기고, 돌리고, 뗀다. 위치·회전은 저장되어 다시 열어도 그대로다.
- **내부**: 구매품이 처음 담길 때는 기본 위치에 놓이고, 이후 사용자가 끌어서 옮기거나 돌릴 수 있다. 같은 데이터에서는 항상 같은 배치를 보여 준다(무작위 재배치 금지).
- 겹침은 물건을 알아볼 수 있는 범위에서만 허용한다. 상품명·구매 상태·터치 영역을 다른 물건으로 가리지 않는다.
- 물건이 많아지면 무한히 겹치지 않고 '구매 리스트' 보기로 전환할 수 있게 한다.
- 시각 배치와 접근 가능한 읽기 순서를 분리한다. 모든 구매품은 구매 리스트(정렬된 행)에서도 접근할 수 있다.
- 편집 도구(스티커 시트)는 아래 시트로 접고 펼치며, 접힌 상태에서 캐리어를 가리지 않는다.

### 목록·저장·매거진·지도: 정돈된 그리드

- 정렬된 행·카드·필드를 사용한다. 컷아웃은 판단을 돕는 썸네일이다.
- 이름·가격·우선순위(꼭 살래·고민)·구매 상태를 빠르게 비교할 수 있어야 한다.
- 행·버튼·필수 필드의 회전, 장식 겹침을 금지한다.
- 입력 중 이미지나 상태 메시지가 나타나도 핵심 조작 위치가 흔들리지 않게 한다.

## 9. Screen Direction

| 화면 | 사용자가 얻을 것 | 표현 방향 | 우선 행동 / 피할 것 |
|---|---|---|---|
| 로그인·여행 생성 | 첫 여행 만들기 | 실사 배경 + 3단계(여행지 → 일정·예산 → 캐리어 색) | 다음 단계로 진행 / 단계마다 질문 하나 이상 묻지 않기 |
| Home (목록) | 이번 여행의 구매 후보와 우선순위 | 그리드·리스트 전환, 정렬·카테고리 칩, 합계 | 상품 상세·우선순위 다시 고르기 / 광고형 배너·관광지 hero 피하기 |
| 저장 · 스크린샷 추출 | 발견한 물건을 짧게 저장 | 저장 방법 4가지 타일 → 추출 결과 목록 | 우선순위 정하기로 이어짐 / 추출 실패 시 직접 입력 경로 제공 |

| 제품 상세 · 현지어 카드 | 가격·후기 확인, 현지에서 묻기 | 큰 컷아웃 + 정렬된 정보, 현지어 카드는 크게 | 샀어요·지도·현지어 카드 / 상세를 쇼핑몰·추천 피드로 확장하지 않기 |
| 지도 · 매장 상세 | 근처 매장에서 무엇을 살 수 있는지 | 지도 위 매장 핀·여행자 발견 깃발, 매장 카드 | 상세보기·길찾기 / 핀과 카드 위치 연동 |
| 매거진 | 다른 여행자의 발견 보기·저장 | 에디토리얼 커버 + 2열 사진 그리드 | 작성글 열기·내 여행에 저장 / 랭킹·보상 경쟁 요소 피하기 |
| 작성글 · 프로필 · 글쓰기 | 발견의 위치·가격 확인, 내 발견 올리기 | 사진 캐러셀, 영수증형 정보 카드, Apple 메모식 서식 툴바 | 저장·댓글·구독 / 위치 없는 발견은 올리지 않기 |
| Carry 리스트 | 여행별 캐리어 모음 | 여행마다 캐리어 카드 | 캐리어 열기 / 후보만 있는 여행을 구매품처럼 보이게 하지 않기 |
| Carry 꾸미기 | 산 물건 컬렉션 + 나만의 캐리어 | 겉면(스티커)·내부(구매품) 전환 | 구매품 눌러 후기 남기기, 스티커 붙이기 / 편집 도구가 컬렉션을 가리지 않기 |

빈 Carry는 첫 저장 또는 첫 구매로 연결한다. 후보만 있는 상태에서는 Carry 내부를 비워 둔다. 로딩·오류·이미지 없음·빈 상태를 모든 화면의 정식 상태로 설계한다.

### 사용성 vs 감성의 판단

- Carry·스와이프: 재미와 시각적 매력을 먼저 검토하되, 기록 열기·되돌리기는 즉시 찾을 수 있게 한다.
- 목록·저장·지도·매거진: 과업 성공과 정보 식별을 먼저 검토한다. 감성 연출이 저장·비교·다시 찾기를 늦추면 줄인다.
- 같은 표현도 화면 역할에 따라 허용 여부가 다르다. Carry의 겹침·회전을 목록에 복사하지 않는다.

## 10. Interaction Direction — 화면 역할에 따라

| 유형 | 적용 화면 | 예 | 제한 |
|---|---|---|---|
| Physical | Carry(겉면·내부), 우선순위 스와이프 | 스티커 끌어 붙이기·돌리기, 구매품이 캐리어에 담기는 낙하, 카드 던지기 | 조작의 결과를 보여 주는 연출만. 끝날 때까지 다음 조작을 막지 않는다 |
| Micro | 목록, 저장, 상세, 지도, 매거진 | 버튼 눌림, 저장 완료 토스트, 하트·구독 상태 변경, 칩 선택 | 결과는 색 외에 글자·아이콘으로도 전달 |
| Discovery | Carry 내부, 지도 | 구매품을 눌러 후기 팝업, 핀을 눌러 매장 카드 | 조작 단서를 제공하고, 필수 정보를 숨기지 않는다 |
| Cinematic | (후속) 온보딩, 여행 리캡 | – | 낮은 빈도, 건너뛰기 가능. 이번 MVP 필수 아님 |

제작 규칙:

- 저장·우선순위·구매 상태는 즉시 반영한다. 애니메이션이 끝나야 다음 행동을 할 수 있게 만들지 않는다.
- 끌기(drag) 조작에는 같은 결과를 내는 버튼·키보드 대안을 둔다. 예: 스와이프 ↔ 방향키·버튼, 스티커 떼기 ↔ 두 번 누르기 또는 삭제 버튼.
- 지속적인 흔들림, 자동 회전, 배경 parallax, 화면마다 축포를 쓰지 않는다.
- 같은 행동에는 같은 피드백을 준다. 한 번의 상태 변경에 여러 연출을 겹치지 않는다.
- **Reduce Motion**에서는 이동·회전·spring을 없애고 정적 상태나 짧은 fade로 바꾼다. 끌어서 배치하는 기능 자체는 유지하되, 낙하·던지기 연출만 생략한다.
- timing·easing은 `Design.md`에서 관리한다. 확인 전에는 spring(damping 30, stiffness 320) 또는 200ms 내외 전환을 임시 기준으로 쓴다.

## 11. 범위 경계

이번 첫 버전에 **포함**한다: §1의 포함 범위 전체(피그마 「시안2」).

이번 첫 버전에 **포함하지 않는다**:

- 일별 전체 일정표, 항공·숙박 예약, 자동 동선 최적화 등 full itinerary planner.
- 실제 결제·주문 대행.
- 보상·레벨·랭킹 등 게임 경제 시스템. (포인트 표시는 있으나 경쟁 요소로 키우지 않는다)
- 캐리어 3D 모델, 사용자가 직접 그리는 스티커 제작, 폰트 변경 등 꾸미기 범위를 넘는 customization. 캐리어 색은 여행 생성 시 5가지 중 고른다.
- 일반 관광·맛집 추천 피드. 매거진은 '여행자가 발견한 물건' 중심을 유지한다.
- AI 추천을 이 아트 디렉션만을 근거로 추가하는 것.

저장과 목록에는 익숙한 탐색 패턴을 쓴다. Packit의 개성은 Carry 컬렉션과 꾸미기, 스와이프의 손맛에서 드러낸다.

## 12. Figma 및 Claude Code/Codex 적용

1. 화면마다 목적, 다음 행동 하나, 후보/구매 상태, 필요한 데이터를 먼저 명시한다.
2. Carry의 오브젝트 영역과 조작 영역(시트·탭·버튼)을 분리한다. 목록·저장·매거진은 Auto Layout과 정렬된 정보 구조를 우선한다.
3. Figma Variable과 코드 토큰은 §5의 의미 역할 이름을 공유한다(예: `text/tertiary`, `button/ink`, `brand/strong`).
4. 모든 값은 §6.2 짝수 규칙을 따른다. 새 규격이 필요하면 제안·적용 위치·이유를 기록한다.
5. 기본·선택·구매 완료·로딩·빈 상태·오류·이미지 없음·Reduce Motion 상태를 표현한다. 구현하지 않는 기능을 동작하는 것처럼 노출하지 않는다.
6. 샘플 데이터와 실제 데이터를 구분한다. 가격·매장 등 없는 사실을 이미지에서 추측해 채우지 않는다.
7. 데이터가 적을 때와 많을 때, 긴 상품명, 서로 다른 이미지 비율, 글자 확대로 검수한다.
8. 결과 보고에는 적용한 방향, 미해결 토큰 충돌, 검증 여부를 분리해 적는다.

## 13. 완료 기준과 추가 관찰 제안

**확정 통과 기준**: 타깃 사용자(일본 쇼핑 여행을 가는 2030) 5명 중 최소 4명이 각자 도움 없이 아래 다섯 단계를 모두 마친다. 참가자별로 전체 흐름을 기준으로 통과 여부를 기록한다.

1. 발견한 물건을 구매 후보로 저장한다.
2. 앱을 다시 열고 목록에서 앞서 저장한 물건을 찾는다.
3. 그 물건을 구매 완료로 표시한다.
4. Carry를 열어 그 물건이 자신의 구매 기록에 담긴 것을 확인한다.
5. 캐리어 겉면에 스티커를 붙여 꾸민다.

**검증 제안** (관찰 결과는 개선에 쓴다):

- 첫 저장과 다시 찾기에 걸린 시간, 멈춘 지점과 이유.
- Carry를 열었을 때 무엇이 모여 있다고 이해하는지, 목록의 후보와 구분하는지.
- 스티커 붙이기·옮기기·떼기를 안내 없이 발견하는지.
- 스와이프 방향(꼭 살래·안 살래·고민)을 처음에 이해하는지, 되돌리기를 찾는지.
- 구매품이 하나일 때와 여러 개일 때, 사진이 없는 구매품이 있을 때도 기록을 식별하고 여는지.
- 기본 모션과 Reduce Motion에서 같은 조작을 할 수 있는지.
- (선택) 지도·현지어 카드·매거진 저장은 핵심 기준과 별도 과업으로 관찰한다.

5명은 핵심 흐름의 과업 성공을 보는 작은 표본이다. 결과를 일반화하지 않고, 실제 재방문율은 별도로 관찰한다.

## 14. QA Checklist

체크가 채워지지 않은 상태를 완료나 검증 통과로 보고하지 않는다.

### Creative Intent 및 범위

- [ ] Carry를 열면 실제 구매품의 컬렉션이 한눈에 보인다.
- [ ] 후보와 구매 완료가 명확히 구분된다(목록의 '꼭 살래·고민' vs Carry의 구매품).
- [ ] 정돈된 UI와 실제 오브젝트·꾸미기의 재미가 함께 느껴진다(50:50 인상).
- [ ] §11의 제외 항목이 화면에 들어가 있지 않다.

### 비주얼

- [ ] UI 색이 §5 팔레트와 일치하고, 무지개·형광·warm beige·장식용 다색이 없다.
- [ ] 상태색은 §5.3 허용 목록만 쓰고, 항상 글자·아이콘과 함께 쓴다.
- [ ] 그림자는 떠 있는 요소에만 있고 §5.4 값을 넘지 않는다. 콘텐츠 카드·hover lift·bevel에 그림자가 없다.
- [ ] Noto Sans KR이 모든 화면의 제목과 본문에 적용되었다.
- [ ] 모든 레이아웃 값이 짝수다(크기·간격·라운드·글자·줄 높이).
- [ ] 상품 컷아웃의 외곽·비율·라벨·실물 색이 보존되었고 인공 그림자가 없다.
- [ ] Carry의 배치·스티커가 구매품 식별과 조작을 가리지 않는다.
- [ ] 목록·저장·매거진의 정보·입력·상태가 정돈되어 있다.

### 사용성과 접근성

- [ ] 저장, 우선순위, 구매 완료, 기록 열기, 꾸미기의 결과가 명확하다.
- [ ] 색만으로 상태를 구분하지 않는다.
- [ ] 일반 글자 4.5:1, 큰 글자·아이콘·필수 경계 3:1을 실제 배경별로 확인했다(사진 위 글자 포함).
- [ ] 최소 44×44px 터치 영역, 키보드 포커스, 접근 가능한 레이블·읽기 순서를 확인했다.
- [ ] 끌기 조작마다 버튼·키보드 대안이 있다.
- [ ] 빈 상태·오류·컷아웃 실패·긴 상품명·글자 확대를 확인했다.
- [ ] Reduce Motion에서도 같은 기능과 상태 정보에 접근할 수 있다.

### 구현 및 문서 정합성

- [ ] Figma와 코드가 같은 의미 역할 이름과 컴포넌트 상태를 쓴다.
- [ ] §3의 '별도 업데이트가 필요한 항목'이 처리되었거나 수정 목록에 남아 있다.
- [ ] 수정하지 않은 `Design.md`를 수정 완료로 보고하지 않았다.
- [ ] 완료 기준 결과를 참가자별 전체 흐름으로 기록하고, 추가 관찰과 구분했다.
